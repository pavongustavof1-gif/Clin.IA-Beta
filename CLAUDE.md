# Clin.IA — guide for Claude Code

Flask + Supabase medical-notes app (Mexico, Spanish UI). Doctors record a consultation → AssemblyAI transcribes → Gemini extracts a SOAP note → doctor reviews/edits → confirms (note is then immutable, NOM-024; corrections are addenda) → PDF with a consent letter + the note. Currently **Beta 1** (live with two real doctors, version 0.8.11-beta); **Beta 2** is being planned/built.

**Source of truth for Beta 2 scope and strategy:** `ClinIA_Hoja_de_Ruta_Beta2_v<latest>.md` in iCloud: `~/Library/Mobile Documents/com~apple~CloudDocs/AI/TAS/ClinIA/Roadmap/Beta 2/` (not in this repo; highest version number wins; items are numbered `#45…`). Read it before starting any Beta 2 work.

## Layout
- `backend/` — Flask app (`app.py` routes + background job worker, `auth.py` JWT/JWKS + roles, `llm_processor.py` Gemini call + CIE-11 step, `extraction_core.py` the pure prompt/parser/validator shared with the bake-off, `transcription.py`, `pdf_generator.py` ReportLab, `icd_service.py` CIE-11, `email_service.py` Resend, `config.py` env).
- `backend/static/` — vanilla JS (no build step, no framework): `app.js` (main app), `admin.js`, `auth-common.js`, `utils.js`, `style.css`. `backend/templates/` — Jinja pages.
- `landing/` — separate static marketing site (own Render static site; no link to the backend). **It deploys separately from the app**: a change under `landing/` (including `landing/legal/`) is live only after the landing static site is redeployed on Render.
- `legal/` — legal documents. `legal/source/*.md` (Términos, Aviso para Usuarios, Aviso para Pacientes; v1.2 Beta, Octubre 2026) is the ONLY place to edit them. `python3 legal/build_legal.py` (stdlib, no build step on Render) regenerates and you commit: `landing/legal/` (index + one page per document, all noindex, printable), the landing's Términos/Aviso-usuarios modals (between `<!-- legal:begin/end … -->` markers in `landing/index.html`), and `backend/templates/legal/aviso_pacientes.html` (included in the app's avisoModal). In that app copy only, the Responsable placeholders (nombre ×2, cédula, domicilio ×2) get `data-responsable` keys (`APP_RESPONSABLE_FIELDS`; the script fails if the counts change), and `static/app.js` fills them on first open from `GET /api/aviso-responsable` (medico/admin; the caller's own nombre, cédula and clinic `direccion`; empty or failed values are left out and keep their bracket; auxiliar gets 404, so every bracket stays). Never `usuarios.email`: the Correo line stays bracketed. The landing's /legal page keeps every bracket. `tests/test_legal.py` fails if any generated file is stale. A new version: bump `VERSION`/`FECHA`/`VERSION_STAMP` in the script, list the old version under "Versiones anteriores", and bump `Config.TERMINOS_VERSION` if the Términos or Aviso para Usuarios changed.
- `backend/tests/` — pytest suite; `backend/tests/frontend/` — browser harness for JS.
- `.github/workflows/auth-tests.yml` — CI runs the pytest suite on push/PR to `main` (Python 3.11 to match `backend/Dockerfile`; dummy env vars only).

## Working rules (user's explicit preferences)
- **Git:** never commit or push unless told. "commit" ≠ "push" — push only when the instruction says so. Branch only when asked. Finished work usually goes to `main` by fast-forward (`git merge --ff-only`), push, then delete the branch (local + remote).
- **Deploys are manual** (the user deploys on Render); pushing to `main` does not deploy.
- **Version bump on every merge to `main`, in 3 places** — `backend/app.py` (`/api/health` `'version'`), `backend/templates/index.html` header badge, and its footer string. Grep for the old version afterwards to catch strays.
- **Investigate → report → implement** for anything non-trivial or ambiguous: reproduce first, show evidence (file:line, before/after), and stop for review when asked to "report but don't fix". Prompts arrive as markdown spec files; follow their report-back list.
- **Trace, don't assume.** Say "confirmed by reading X" only after reading X. Verify third-party API shapes (Supabase Admin API, PostgREST JSONB filters) against real docs.
- **Ask when a spec conflicts with existing code** (naming, behavior) rather than silently choosing.
- **No PHI anywhere** — logs, fixtures, tests, sample PDFs. Synthetic data only. Never log transcript or patient content.
- Disclose what was and wasn't verified (e.g. "not verified: real Supabase round-trip").
- Keep changes scoped to the task; no unrelated refactors. Match surrounding comment density and style (this codebase explains the *why*).

## Codebase gotchas
- **CIE-11 policy (0.8.5):** a code comes **only** from the WHO lookup (`icd_service.lookup_cie11`) or from the doctor, **never from Gemini**: `llm_processor.apply_cie11_lookup` deletes any `codigo_cie11`/`titulo_cie11`/`cie11_fuente` Gemini returned before the lookup, and the prompt says not to include them. The lookup takes the highest-`score` entity that has a code (an empty `theCode` is no result: no code, no title); WHO clusters (`5A24/5A11`, `GB51&XK8G`) are valid codes. `evaluacion.cie11_fuente` is `oms` (lookup) or `medico` (typed/changed by the doctor), absent with no code; it's never printed on the PDF. `titulo_cie11` exists only while the code equals the WHO value — any other code has no title. At confirm, `app.reconcile_cie11` normalises the code (trim, uppercase, no spaces) and sets the source by comparing with the WHO value on the **pending** note (not the client's claim). Format: `icd_service.CIE11_CODE_PATTERN` (ICD-11 Reference Guide §1.2.4.1, §2.9, §2.10; mirrored in `app.js`, a test keeps them equal) only **warns** on the review screen — a malformed code is never rejected; the doctor is responsible. `normalize_evaluacion` maps `diagnostico_principal` → `diagnostico` before the lookup. Whether a cluster is acceptable in a signed note is a clinical call, not enforced in code. The shared renderer (`session-detail-render.js`: result summary, Historial, admin session view) shows "Código CIE-11: <code> — <title>" and Pronóstico; `cie11_fuente` is never displayed. `ICD11_RELEASE_VERSION` must be `YYYY-MM`: checked once at import (`icd_service.configure_release`); empty/malformed logs one error and disables the lookup (outcome `not_configured`). Token refresh is locked; a token failure or an unreachable/timed-out WHO endpoint is cached for 60 s (`FAILURE_CACHE_SECONDS`), during which lookups are skipped.
- **CIE-11 lookup chain (0.8.7):** WHO's regular search only returns entities containing *all* the query's words, so descriptive diagnoses ("Lumbalgia por contractura muscular…") found nothing. `icd_service.lookup_cie11(diagnostico, term)` tries, first coded **and relevant** result wins (same highest-score / coded-entity rule at each search): **full** `/search` on the whole diagnosis → **term** `/search` on `termino_busqueda_cie11` (skipped if absent or equal to the diagnosis) → **autocode** `/autocode` on the whole diagnosis → **autocode_term** `/autocode` on the accepted term (0.8.9; skipped without one); both kept only if `matchScore >= Config.CIE11_AUTOCODE_MIN_SCORE` (0.80; WHO documents no default) and saved **without a title** (autocode returns none). Any HTTP error, timeout or bad JSON stops the chain (no retries inside a job); timeouts feed the 60 s failure cache. **No flexible search (0.8.8):** 0.8.7 had a `useFlexisearch=true` stage ("results do not have to contain all of the words"); in production it turned "Control glucémico inadecuado" into MB24.64 "Afecto inapropiado" — a wrong code is worse than none, so it was removed; don't add it back. **Relevance check (0.8.8; synonyms 0.8.9):** a stage's result must share at least one content word with the text that stage searched (the diagnosis, or the term at the term/autocode_term stages). A search entity passes on its title **or** any `matchingPVs[].label` (`icd_service.is_relevant_entity`; v2 spec `ISimpleEntity.matchingPVs` "List of property values that match the search string", `ISimplePropertyValue.label`; highlight markup stripped) — so term "Lumbalgia" → ME84.2Z "Dolor lumbar, sin especificación" is accepted via its matched label "Lumbalgia" (production 0.8.8 rejected it); autocode passes on `matchingText` (`is_relevant`); same normalisation as the term guard (`icd_service.content_words`: lowercase, no accents, whole words, Spanish stopwords ignored); otherwise it's `outcome=irrelevant` and the chain continues. Only the top-scored entity is checked — a lower one is never promoted in its place. Remaining cost: if WHO returns no `matchingPVs` (the spec doesn't say when it's omitted) and the title shares no word, a true synonym is still rejected and the doctor types the code. The term comes from Gemini (prompt rule 9: shortest standard wording of the principal condition, only words from its own diagnosis, never a code); `llm_processor.accept_search_term` keeps it only if every content word (lowercased, accent-free, Spanish stopwords ignored) is in `diagnostico`, otherwise it's dropped with `outcome=term_rejected`. `apply_cie11_lookup` pops the term before the lookup and `reconcile_cie11` drops it at confirm, so it never reaches the review screen, the saved note or the PDF. The Diagnóstico itself is never changed.
- **`service_role` GRANTs:** Supabase PostgREST needs explicit GRANTs. Before a new table, or the first use of a new operation type (SELECT/INSERT/UPDATE/DELETE) on an existing table, check grants and hand the user the exact `GRANT` SQL. From 30 Oct 2026 Supabase stops auto-exposing new tables: every new table needs `GRANT SELECT, INSERT, UPDATE, DELETE ON public.<table> TO service_role` (never anon/authenticated; serial columns also need the sequence GRANT; missing grants fail with 42501). A past DELETE route failed 100% in prod this way.
- **Roles (`usuarios.rol`):** `admin` = clinic admin who is also a doctor (records notes, admin panel); `medico` = doctor; `auxiliar` = clinic admin who is NOT a doctor (admin panel only, no cédula, never records/confirms/reads notes as a doctor — `/` redirects them to `/admin`). Never compare rol strings: use `auth.is_admin_role` (admin, auxiliar) / `auth.is_medico_role` (admin, medico), and `isAdminRole`/`isMedicoRole` in `utils.js`. `POST /api/admin/usuarios` creates `medico`, `admin` (shown as "Médico administrador"; same required fields as médico) or `auxiliar`; clinica_id always from `g.usuario`. UI labels live in `utils.js` `ROL_LABELS`: admin "Médico administrador", medico "Médico", auxiliar "Auxiliar administrativo". A clinic must keep ≥1 active admin/auxiliar (`_would_leave_clinic_without_admin`).
- **Authorization conventions:** every data route uses `@require_auth` (+ `@require_admin` for admin routes, or `@require_medico` for routes that record, confirm or read the caller's notes — an auxiliar gets 404 there). Out-of-scope or missing resources return a uniform **404, never 403** (a distinguishable 403 leaks existence; `require_admin`'s 403 predates this and is left as is). Read scope = owner OR same clinic (`caller_can_read_session`); write/sign scope = owner only (`caller_can_addend_session`). Admin routes are limited to the admin's own clinic with server-built filters.
- **Single-instance assumption:** the rate limiter (`memory://`), JWKS cache, `_usuario_cache`, logo cache and startup job reaper are per-process. Correct only with one gunicorn worker/instance (current Dockerfile).
- **Render deploys keep the old instance alive until the new one is healthy**, but jobs running on the old instance are interrupted — don't deploy with `trabajos` rows in `queued/transcribing/extracting`.
- **CSP:** inline scripts need the per-request nonce (`g.csp_nonce`); same-origin external scripts are fine. Page config reaches static JS through `window.CLINIA_CONFIG`.
- **AssemblyAI speech model is pinned (#89, 0.8.10):** `transcription.SPEECH_MODELS = ["universal-3-5-pro"]` is sent as `speech_models` (the singular `speech_model` is deprecated upstream; SDK 0.64.2 types the plural as `List[str]`, so no upgrade was needed). Pinned so results don't shift when AssemblyAI's default list changes. One INFO line per job, `ASR: speech_model=<speech_model_used>` (model name only). `tests/test_transcription_speech_model.py` asserts the exact request body the SDK builds.
- **Gemini is non-deterministic.** The same recording can yield differently worded notes; that is not a pipeline bug. The note the doctor reviews is frozen: `confirm_and_generate` renders the submitted `structured_data` verbatim (no second extraction).
- **Pure extraction core (#83, 0.8.11):** `extraction_core.py` holds the prompt, `clean_json_response`, `validate_against_schema`/`normalize_evaluacion` and the pure CIE-11 term helpers (`accept_search_term`, `content_words`); `llm_processor` and `icd_service` import them, and the bake-off harness uses the same module. It must stay **stdlib-only** — no config/dotenv/flask/supabase/google/logger/icd_service imports, no env reads at import (`tests/test_extraction_core.py` checks this in an empty-env subprocess). The prompt is pinned byte-for-byte by `tests/fixtures/prompt_golden_*.txt`: a deliberate prompt change means regenerating those goldens in the same commit. `extraction_schema.json` (draft 2020-12, all fields optional) documents the model output and is kept in sync with the prompt's JSON template by a test; nothing at runtime loads it.
- **`extraction_core.validate_against_schema` (via `llm_processor`) normalizes** `informacion_paciente` and `metadata` to `{}` when Gemini omits them (it is told to omit empty fields); an extraction with no S/O/A/P content still fails on purpose.
- **Medications textarea** joins/splits fields on `" - "` via `MEDICAMENTO_FIELD_SEPARATOR` (a bare `-` collided with "8-12 horas"); untouched medications are sent back as the original objects. The proper fix (separate fields) is roadmap #73.
- **Consent page (PDF):** `_build_consent_page` must fit on page 1 with the note starting on page 2; headroom is only ~2.5 mm in the worst case (roadmap #58 frees space). `tests/test_pdf_consent.py` enforces it.
- **Cédula on PDFs (#55):** `get_usuario_cedula` returns `''` for "no cédula" and `None` for "lookup failed". Every PDF path (confirm, doctor download, admin download) returns 503 "No se pudo generar el PDF. Intente de nuevo." on `None` and never renders; confirm does the lookup before any write, so the note stays `pending_review`. Addendum authors' cédulas are looked up at render time from `author_usuario_id` (never written to `addenda`).
- **Test pitfall:** `conftest.py` patches `app_module.pdf_generator.generate_pdf`; to exercise the real PDF code instantiate `pdf_generator.PDFGenerator()` directly.
- **Public access requests (#53/#54):** `GET /solicitud` (noindex, unlinked, no supabase-js) → `POST /api/solicitudes` (no auth) → `solicitudes_registro`; a superadmin reviews them (Review C). Validation/normalization is in `solicitud_validation.py` and mirrors the table's CHECKs. Honeypot, an existing user and an open request all get the SAME generic 200 (no user enumeration). This flow must never log applicant data: only `Solicitud: req=<id> outcome=<...>`; it uses `_sb_get_quiet` / `_sb_insert_solicitud`, which log table + status only (`_sb_get` logs the full path, which here would carry the email). `TERMINOS_VERSION` (config.py, `ToS-1.2-Beta+AU-1.2-Beta`) is stored with each request — bump it when the Términos or Aviso para Usuarios changes. `SUPERADMIN_EMAIL` / `SUPERADMIN_USER_IDS` are optional env vars (unset = off; see Superadmin below). The form's checkbox links go to `clinianotes.com/legal/terminos/` and `/legal/aviso-usuarios/`; `GET /aviso-privacidad-usuarios` is a 301 to the latter (inventory field `public_status`). The old `clinianotes.com/#terminos` deep link still opens the landing's Términos modal. `recomendado_por` is set to null in the same PATCH that marks a request aprobada or rechazada (the Aviso para Usuarios promises it).
- **Superadmin (#53, Review C):** `Config.SUPERADMIN_USER_IDS` (env, comma-separated, lowercased; empty = nobody) names the one person who reviews `solicitudes_registro` at `/superadmin`. Every `/api/superadmin/*` route uses `@require_superadmin` INSTEAD of `@require_auth`: it authenticates itself and answers 404 `{"error": "No encontrado"}` to everyone else — no token, bad token, inactive user and any non-superadmin alike (inventory field `superadmin_required`). `/api/session-check` adds `"superadmin": true` only for that user (key absent otherwise), which reveals the header link, plus `"solicitudes_pendientes": N` (estado pendiente OR en_proceso; `_sb_count_quiet`, a HEAD with `Prefer: count=exact`; the key is omitted if the count fails, and session-check never fails over it). N > 0 shows the amber, non-dismissible banner under the nav on `/` and `/admin` (`utils.js showPendientesBanner`, `static/pendientes-banner.css`), never on `/superadmin`. These flows must never log email/cédula/teléfono/domicilio: use `_sb_get_quiet`, `_sb_patch_returning_quiet`, `_sb_delete_quiet`, `_sb_count_quiet` and the Auth admin helpers (`_sb_get_auth_user`, `_sb_delete_auth_user`, `_sb_generate_recovery_link`), which log table/endpoint + status only; the one log line is `Superadmin: solicitud=<id> accion=<...> outcome=<...>`.
- **Approval rules (`POST /api/superadmin/solicitudes/<id>/aprobar`):** new clinic (`clinica_id: null`) ⇒ rol admin or auxiliar; existing clinic + admin/auxiliar ⇒ `confirma_admin: true`; admin/medico ⇒ the request has cédula + especialidad; auxiliar ⇒ only if `rol_solicitado` was auxiliar; the email must have no usuarios row (re-checked at approval, 409 leaves it pendiente). It is a resumable state machine — each step is recorded on the solicitud before the next: claim (pendiente→en_proceso, conditional PATCH) → clinic (created + `clinica_creada`, or chosen) → auth user (`usuario_id` stored via `_provision_usuario(on_auth_user=...)` BEFORE the usuarios insert) → usuarios row → `aprobada` → invite → notices to the clinic's other active admins. A retry skips what is recorded; an unrecorded new clinic is deleted again. Emails never undo an approval. Resend/a resumed approval use a `recovery` link (existing user; never creates one), which /set-password receives as PASSWORD_RECOVERY. "Invitation accepted" = auth user's `email_confirmed_at` set. Delete only for aprobada + not accepted + no sesiones/trabajos/lecturas_sesion; it removes the clinic only if `clinica_creada` and empty. Rechazadas older than 30 days are purged on every list load and at startup. The rejection email text is a legal DRAFT in `email_service.REJECTION_EMAIL_DRAFT` (the page previews that same dict).
- **Rate limits in tests:** `conftest.py` resets the memory:// limiter before/after every test; `test_solicitudes.py` moves `time.time` to test day windows.
- New/independent UI or tables get their own scoped CSS/logic, not edits to shared rules.
- Prefer ref-based element clicks (`read_page`/`find`) over screenshot pixel coordinates when driving the Browser tool.

## Observability (0.8.6)
Two log lines, enums and numbers only — **never** the URL, the query (diagnosis), the code or the title; tests assert this:
- Per lookup stage (one line per stage tried, so 1–4 per job, plus a `term_rejected` line when the guard drops the term): `ICD: outcome=<ok|no_results|no_code|low_score|irrelevant|http_NNN|timeout|token_failed|not_configured|bad_json|no_diagnosis|term_rejected> stage=<full|term|autocode|autocode_term|none> cluster=<0|1> ms=<n>`, plus ` score=<0.00–1.00>` on autocode/autocode_term lines. `stage=none` = the chain never started (no diagnosis, not configured, cached failure, no token). `timeout` also covers an unreachable endpoint; during the 60 s failure cache the same outcome repeats with `stage=none ms=0`. `ok`/`no_results`/`no_code`/`low_score`/`irrelevant`/`no_diagnosis`/`term_rejected` are INFO, the rest WARNING.
- Per signed note: `CIE11: session=<id> fuente=<oms|medico|none> cambio=<kept|changed|cleared|added|absent>`, logged after the confirmed save succeeds; `cambio` compares the pending note's code with the confirmed one.
- Reading them in Render: the service → **Logs**, search `ICD: outcome=` or `CIE11:` (e.g. `outcome=timeout`, `cambio=changed`). Healthy: mostly `outcome=ok` (`stage=` shows which step found it — a high share of `stage=autocode` deserves a look at the codes doctors then change; `irrelevant` counts how often WHO's best match shared no word with the search; `low_score` lines' `score=` is what to calibrate `CIE11_AUTOCODE_MIN_SCORE` against); many `term_rejected` means Gemini isn't following prompt rule 9; a run of `not_configured` means credentials or `ICD11_RELEASE_VERSION` are wrong (look for the one `ICD11_RELEASE_VERSION ... disabled` error at startup); `token_failed`/`timeout` bursts mean WHO is down or unreachable. The share of `cambio=changed|cleared` vs `kept` is how often doctors override the WHO code. Render keeps logs only for a limited time, so copy counts out if a trend matters.

## Beta 2 test & deploy strategy (roadmap v3+)
No maintenance window and no staging. Beta 2 features ship dark behind **per-clinic feature flags** (`BETA2_CLINICAS` env var on Render; the server decides and reports active features via `/api/session-check`), are tested in production in the "Clínica de Pruebas" with fictitious patients (confirmed notes there are permanent), then released to all clinics by changing the flag. Note: changing a Render environment variable restarts the service (interrupting in-flight jobs like a deploy); roadmap #47 decides whether flags live in an env var or in a feature_flags table (recommended, no restart). Migrations are additive only, with a manual backup first (Sprint 8 is the exception: separate Supabase project). Release each sprint's features before starting the next. Details and rationale: the roadmap's "Estrategia de pruebas y despliegue".
